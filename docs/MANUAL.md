# Technical manual — implementation harness in a new project

This manual describes how the implementation environment works and how to turn it on in a repository that has none of it yet. The environment has two halves:

- **Generic**, in the `wh` plugin (repo `wh-harness`, installed per user): the procedures of the skills, agents and hooks. It holds for every project and never cites a project command.
- **Project-side**, versioned in the repo (`.claude/profile/`): the facts the generic half cannot discover on its own (commands, ports, docs, limits, sources of the glossary and of the feature map).

The rule that holds the two halves together: **the skill has the procedure, the profile has the facts.** A skill cites a profile section (`profile § Tests`), never a command. Since 0.7.0 everything in the plugin and in this repo is written in English (skills, profile templates, agents, scripts, docs); the `##` headings of a project's profile are those of the English template (`## Tests`, `## Limits`…). Profiles generated by earlier versions need `/wh:profile` again. Commands (`/wh:adopt`, `/wh:profile`…) and the `.claude/profile/` folder did not change.

## 1. Pieces and where they live

| Piece | Path | Role |
|---|---|---|
| `wh` plugin | `plugins/wh/` (marketplace `wh-harness`) | everything generic; commands `/wh:<skill>`, agents `wh:<agent>` |
| Generic skills | `plugins/wh/skills/<skill>/SKILL.md` | procedure (`implementation`, `cleanup`, `deploy`, `start-app`, `qa-visual`, `feature-docs`, `brainstorm`, `profile`, `retro`, `adopt`; `retro` and `adopt` have no profile: procedure only) |
| Skill profile template | `plugins/wh/skills/<skill>/PROFILE.md` | which `##` sections that skill's profile must have |
| Common profile template | `plugins/wh/skills/profile/COMMON.md` | sections every skill uses |
| Profile generator | `plugins/wh/skills/profile/SKILL.md` (`/wh:profile <skill>`) | writes or completes the profiles from the templates and the repo |
| Adoption | `plugins/wh/skills/adopt/SKILL.md` (`/wh:adopt`) + `scripts/check.py` | diagnoses a new repo and creates what is missing (§4); the script is the deterministic diagnosis |
| `/wh:implementation` support | `plugins/wh/skills/implementation/TRIAGE.md`, `LANES.md`, `ENVIRONMENT.md`, `REPORT.md`, `scripts/` | triage and plan format; parallel lanes; agent environment and protocol; retros and report; `preflight.sh` and `scope.sh` |
| Manifests | `plugins/wh/.claude-plugin/plugin.json` and `icon.png`, `plugins/wh/README.md`, `.claude-plugin/marketplace.json` | what the plugin directory reads; `claude plugin validate --strict` on both (§6) |
| Agents | `plugins/wh/agents/impl-enrich.md`, `impl-dev.md`, `impl-qa.md` | subagents of `/wh:implementation` (`subagent_type: "wh:impl-dev"`…) |
| Hooks | `plugins/wh/hooks/hooks.json`, `plugins/wh/scripts/` | deterministic hooks; today `prompt-graph` (only runs with `context.json` in the cwd or above) |
| Project common profile | `<repo>/.claude/profile/_common.md` | clone, toolchain, git, ports, navigation, docs, limits |
| Per-skill profile | `<repo>/.claude/profile/<skill>.md` | only what that skill uses; cites `_common § X` instead of repeating |
| Hook sources | `<repo>/.claude/profile/context.json` | turns `prompt-graph` on in the project and says where glossary, features and CodeGraph are |
| Plugin declaration in the project | `<repo>/.claude/settings.json` | makes whoever clones the project receive the plugin (§4) |
| Graph cache | `~/.cache/walter-harness/<hash of the repo path>.json` (or `$WH_CACHE_DIR`) | generated; never version it |

## 2. Mechanism 1 — profile injection into the skills

Each generic skill starts with a Claude Code preprocessing command, which runs **before** the model reads the skill and pastes its output into the text:

```markdown
Project profile (injected; `PROFILE_MISSING` = phase 1 writes the profile before going on):
!`cat .claude/profile/_common.md .claude/profile/implementation.md 2>/dev/null || echo PROFILE_MISSING`
```

Flow:

1. The user calls `/wh:implementation …` at the repo root.
2. The `cat` runs in the session directory. If the profiles exist, their content enters the skill; if not, the word `PROFILE_MISSING` does.
3. With `PROFILE_MISSING` or a missing section, the skill calls `Skill(wh:profile, "<skill>")` before going on.
4. The `profile` skill compares the file with the template (`PROFILE.md` or `COMMON.md`), looks for each missing section in the repo's sources (in order: `CLAUDE.md`/`AGENTS.md` and the docs they point at, profiles already written, the project's old skill, `.github/workflows/*`, build scripts, `README`) and writes one line per fact with the source in brackets (`[ci: tests.yml]`, `[inferred]`…). `[inferred]` lines go to the owner, one question per profile section, up to 4 per call (with the `defer` argument, the caller asks: `/wh:implementation` merges them with the enricher's questions). A section with no answer stays `—`, and the skill skips the phase that depends on it, saying so.

Paths to the plugin's own files (templates, scripts, the retro) are written as `${CLAUDE_PLUGIN_ROOT}/skills/…`; Claude Code replaces the variable with the real path when loading the skill (tested; `${CLAUDE_SKILL_DIR}` also works). Agents do not receive the variable resolved: `/wh:implementation` passes `PLUGIN_ROOT=<path>` in each subagent's prompt.

Practical consequences:

- **The profile is read only by the skill.** It does not load on its own in the session; that is why it can be dense and factual.
- **Target size:** `_common.md` ≤ 40 lines, `<skill>.md` ≤ 60. The excess becomes a repo doc the profile points at.
- **No shadowing:** the plugin's skills have a prefix (`/wh:implementation`), so a project skill with the short name (`<repo>/.claude/skills/implementation/`) coexists with it, but confuses. When migrating a project that already had its own skills, their facts move into the profile and the old folder leaves (`git rm -r .claude/skills/<skill>`).
- **Worktrees:** the profile is versioned, so every agent worktree is born with it.

## 3. Mechanism 2 — `prompt-graph` hook (prompt enrichment)

### 3.1 What it does

On every prompt sent, Claude Code runs the `wh` plugin's `UserPromptSubmit` hook:

```
<walks up the tree from the cwd until it finds .claude/profile/context.json; without it, Python is not even called> python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/prompt_graph.py"     (timeout 5 s)
```

The command uses `python3`; on a native Windows without that name (`python`/`py`), edit the installed plugin's `hooks.json` or create a `python3` alias on the PATH.

The script receives the event as JSON on stdin (`prompt`, `cwd`), matches the text against a domain graph and returns `hookSpecificOutput.additionalContext`. That text enters the model's context together with the prompt. There is no LLM, network or randomness: the same prompt with the same sources always produces the same output.

Example output (from a Portuguese-language project, `idioma: pt`):

```
[wh:prompt-graph] Contexto determinístico (glossário + features + CodeGraph); só ponteiros, confira antes de afirmar.
Evite "vitrine": o termo é Balcão (`Counter`)
Termos: Balcão = `Counter` · Porção = portion (`Portions`)
Ler: docs/features/balcoes.md (Balcões e pratos preferidos) · docs/features/cozinha.md (Cozinha e cardápio)
Interage com: tudo-pronto, fregueses, despensa, clientes, reputacao, decorar
Símbolos: CounterService KittyCaffeeBackend/Src/Services/CounterService.cs:48 · Counter …/Counter.cs:3
```

The output has pointers only and a `max_chars` cap. The model decides what to open. A prompt with no domain term injects nothing.

### 3.2 When it stays silent

- There is no `.claude/profile/context.json` walking up the tree from the `cwd` (projects without the file are never affected).
- The prompt has fewer than `min_prompt` characters.
- No feature passes `min_score` and no term matched.
- The variable `WH_PROMPT_GRAPH=0` is in the session environment.
- Any exception: the error goes to stderr and the prompt proceeds normally. The hook never blocks.

### 3.3 The graph

**Nodes**

- **Term**: each row of the glossary tables.
- **Feature**: each `<features>/*.md`, except `README.md`.
- **Symbol**: identifiers cited in `## Entry symbols` of the features and in the Code column of the glossary.

**Search keys (alias → node, with weight)**

| Origin | Points at | Weight |
|---|---|---|
| Keywords of the feature's row in the index (`README.md`) | feature | 3 |
| `aliases:` in the frontmatter and `# Title` of the feature | feature | 3 |
| Identifier in `## Entry symbols` | feature | 2 |
| Business column of the glossary (parts split by `/` and `,`, without parentheses) | term | — |
| Identifiers in backticks in the Code column | term | — |
| Words in quotes in the Avoid column | term, as an "Avoid" warning | — |

**Edges**

- **Term → feature:** when some key of the term appears in the body of the feature file. Weight 1, split among the linked features.
- **Feature → feature:** `[x](x.md)` links of the `## Interactions` section. They become the "Interacts with" line of the highest-scoring feature.
- **Symbol → `file:line`:** read-only query to the CodeGraph SQLite (`nodes.name`). When the same name appears more than once, the one with the best kind wins (class, then interface, route, method…), outside a test folder and with the shortest path. The `class_name_globs` globs resolve `class_name X` of Godot scripts, which are not in the index.

**Avoid rule:** a quoted synonym only becomes a warning when it is not a proper term of another row. Example: "nível" is avoided in "Tier", but it is the term Nível, so it produces no warning.

### 3.4 Query (per prompt)

1. **Normalization** (the same for prompt and keys): NFKD without accents, lowercase, tokens `[a-z0-9_]+` and a simple PT-BR plural stem (`-ões`/`-ães` → `-ão`, `-ais` → `-al`, `-eis` → `-el`, `-ns` → `-m`, final `-s`). Identifiers become a single token (`CounterService` → `counterservice`).
2. **Greedy n-gram matching**, from the longest (5 tokens) to the shortest. A token already used does not enter a shorter match.
3. **Scoring:** each matched key adds `weight / number of features it points at` to each feature. Each matched term adds 1 split among the features linked to it.
4. **Output:**
   - Avoid warnings (up to 2);
   - terms (up to `max_termos`);
   - features with score ≥ `min_score` (up to `max_features`);
   - neighbors of the first feature (up to `max_interage`);
   - symbols (up to `max_simbolos`): first those cited in the prompt, then the features' entry symbols, alternating between them.

### 3.5 Cache and performance

- **Cache signature:** SHA-1 of the graph version, the script's mtime, and mtime and size of `context.json`, the glossary, each feature and `codegraph.db`. Any change rebuilds the graph on the next prompt.
- **Writing:** atomic (`.tmp` file followed by `os.replace`), safe with several sessions at once.
- **Times measured on KittyCaffee** (29 features, 240 terms, 334 symbols, ~1060 keys): rebuild ~0.18 s; query with a warm cache ~30 ms.
- **Context cost:** about 300 to 900 characters per prompt with a hit and zero without one.

## 4. Turning on a new project — step by step

Two ways to have the plugin:

- **Consumer** (anyone, any machine): from GitHub.

  ```bash
  claude plugin marketplace add Walter-Dalla/wh-harness
  claude plugin install wh@wh-harness
  ```

- **Maintainer** (whoever edits the harness): from the directory, without push. Claude Code copies the plugin to a cache: after editing, run the `update` and open a new session (without it, the next session still loads the old version; seen in Claude Code 2.1.312).

  ```bash
  git clone https://github.com/Walter-Dalla/wh-harness ~/walter-harness
  claude plugin marketplace add ~/walter-harness
  claude plugin install wh@wh-harness
  claude plugin list | grep -A4 'wh@'            # Status: ✔ enabled
  claude plugin update wh@wh-harness             # after each edit in the harness
  ```

**Session model for `/wh:implementation`.** The profile § Models chooses the subagents' model; the orchestrator runs on the session's model, and it pays most of the bill (72–77% of the cost in the two runs of the 2026-10-28 test drive, with the session on the most expensive model). For harness tasks, open the session with `claude --model opus`.

In a new project, the short path is `/wh:adopt` at the root: it runs the diagnosis (`plugins/wh/skills/adopt/scripts/check.py --root .`, one `OK`/`MISSING`/`WARN` line per piece), calls `/wh:profile`, seeds the glossary and the feature map when the repo has a domain, writes `context.json`, `settings.json` and `.gitignore`, and validates with `--build` and a `--query` (§6). `/wh:adopt check` only diagnoses. What it does not do: `codegraph init` (the owner's decision), commit, and fattening the feature map (`/wh:feature-docs`). The steps below are the same path, by hand:

1. **Repo map.** Have a `CLAUDE.md` (or `AGENTS.md`) at the root that says where each thing lives and which docs to read. It is the first source of the `profile` skill.
2. **Common and per-skill profiles.** At the repo root, run `/wh:profile` (all skills) or `/wh:profile implementation` (one only). Review `.claude/profile/_common.md` and `.claude/profile/<skill>.md`, answer the `[inferred]` lines and check that `## Limits` says what no agent touches (production, secrets, the owner's database).
3. **Glossary** (optional, but it is what feeds the hook). Create `docs/GLOSSARY.md` in the format of §5.1.
4. **Feature map** (optional). Create `docs/features/README.md` and one file per feature in the format of §5.2. The `/wh:feature-docs` skill maintains this map once its profile exists.
5. **CodeGraph** (optional). `codegraph init -y .` at the root creates `.codegraph/`. Put `.codegraph/` in `.gitignore`.
6. **Turn on the hook** by creating `.claude/profile/context.json` (`/wh:profile` already writes it when the repo has a glossary or a feature map; with neither it answers "hook off: no sources"):

   ```json
   {
     "glossario": "docs/GLOSSARY.md",
     "features": "docs/features",
     "indice_features": "docs/features/README.md",
     "codegraph": ".codegraph/codegraph.db",
     "class_name_globs": [],
     "idioma": "en"
   }
   ```

   Paths relative to the repo root. A missing source breaks nothing: without a glossary there are no terms; without CodeGraph the symbols come without `file:line` and do not appear on the "Symbols" line.
7. **Declare the plugin in the project** in `.claude/settings.json`, so that whoever clones receives the install offer when trusting the folder:

   ```json
   {
     "extraKnownMarketplaces": {
       "wh-harness": { "source": { "source": "github", "repo": "Walter-Dalla/wh-harness" } }
     },
     "enabledPlugins": { "wh@wh-harness": true }
   }
   ```

   To pin a version, add `"ref": "<tag>"` to the `source`, with a tag that exists (`git tag` in the harness). Without `ref`, the project follows `main`.
8. **Validate** before opening a session (see §6). Then commit `.claude/profile/` and `.claude/settings.json`.
9. **Open a new session.** Hooks and plugins load at session start.

## 5. Source formats

The parser works by markdown convention. Off-format lines are ignored without error.

### 5.1 Glossary

```markdown
## <Any section>

| Business | Code | Avoid / note |
|---|---|---|
| Counter | `Counter` | "display case" |
| Table / chair | `Table` / `Chair` | |
| Customer (anonymous customer) | NPC: `ActiveNpc`, `Npc` | "patron" for the anonymous one |

## Pitfalls

| In the code | Means | Why |
|---|---|---|
| `Entrace` | entrance / door | historical typo |
```

- **Business:** parts split by `/` or `,` become keys. Text in parentheses is a description and does not become a key. Parts shorter than 3 characters are dropped.
- **Code:** only what is in backticks and looks like an identifier (`Name`, `a.b`) or a route (`GET /x`, `POST /x`).
- **Avoid:** only what is in double quotes (3 to 40 characters).
- In the `## Pitfalls` section the columns are read in the order code, meaning and reason. The hook also accepts the Portuguese section names (`## Armadilhas`, `## Símbolos de entrada`, `## Interações`).

### 5.2 Feature map

`docs/features/README.md`: one table row per feature, with the link in the first cell. The other cells become keywords, comma-separated (a comma inside backticks does not split):

```markdown
| File | Feature | Look here when the task talks about… |
|---|---|---|
| [counters.md](counters.md) | Counters (F-04) | counter, portion, `CounterService`, `counter_empty` |
```

`docs/features/<feature>.md`:

```markdown
---
aliases: [Counters, Favorite dishes, F-04]
---

# Counters and favorite dishes (F-04)

## Entry symbols

Backend: `CounterService`, `Counter`, `CounterDto`.
Client: `KitchenStore`.

## Interactions

- **Kitchen** ([kitchen.md](kitchen.md)): …
```

Sections read: `aliases` frontmatter, `# Title`, `## Entry symbols` (only identifiers in backticks) and `## Interactions` (only `[...](x.md)` links). The rest of the body only serves to link glossary terms to the feature.

### 5.3 `context.json`, all keys

| Key | Default | Effect |
|---|---|---|
| `glossario` | `docs/GLOSSARIO.md` | glossary file |
| `features` | `docs/features` | features folder |
| `indice_features` | `docs/features/README.md` | index with keywords |
| `codegraph` | `.codegraph/codegraph.db` | CodeGraph SQLite (opened read-only) |
| `class_name_globs` | `[]` | globs (with `**`) of scripts with `class_name X` |
| `max_features` | `3` | features under "Read" |
| `max_termos` | `4` | terms under "Terms" |
| `max_simbolos` | `5` | symbols under "Symbols" |
| `max_interage` | `6` | neighbors under "Interacts with" |
| `min_score` | `1.2` | minimum score for a feature to appear |
| `min_prompt` | `12` | shorter prompts are ignored |
| `max_chars` | `900` | cap of the injected text |
| `idioma` | `pt` | output labels: `pt` or `en` |
| `secoes` | PT and EN | accepted section names, e.g. `{"simbolos": ["Entry symbols"], "interacoes": ["Interactions"], "armadilhas": ["Pitfalls"]}` |

The key names and the `pt` default are kept for compatibility with projects configured before 0.7.0.

## 6. Validation and debugging

```bash
H=~/walter-harness/plugins/wh/scripts/prompt_graph.py   # in the harness clone

# The harness's own tests (stdlib, no dependencies): hook, scope.sh, preflight.sh, check.py and section references
python3 -m unittest discover -s ~/walter-harness/tests

# Manifests (CI runs both; no login needed)
claude plugin validate ~/walter-harness/plugins/wh --strict
claude plugin validate ~/walter-harness --strict

# Rebuilds and shows the graph size
python3 -I $H --build --root .
# graph: 1059 keys, 29 features, 240 terms, 334 symbols

# Simulates a prompt; --explain shows the matched keys and the ranking on stderr
python3 -I $H --query "the counter does not receive portions" --root . --explain

# Simulates the real hook event
echo '{"prompt":"the counter does not receive portions","cwd":"'$PWD'"}' | python3 -I $H
```

| Symptom | Probable cause | What to do |
|---|---|---|
| Nothing injected on any prompt | no `context.json`, plugin disabled or old session | `claude plugin list`; open a new session |
| The right feature does not appear | prompt word absent from the keywords | `--explain`; add the word to the index or to the feature's `aliases` |
| Many tied features | generic word on many rows | remove the word from the index or raise `min_score` |
| Symbol without `file:line` | outside CodeGraph | `codegraph sync .` or `class_name_globs` |
| Symbol points at the wrong place | repeated name in the index | use the more specific name in `## Entry symbols` |
| False "Avoid" warning | quoted word is also a used term | the filter already covers proper terms; otherwise remove the quotes |
| Stale graph | should not happen (signature by mtime) | `--build`, or delete `~/.cache/walter-harness/*.json` |

**`/wh:implementation` in headless mode** (`claude -p "/wh:implementation …" --output-format stream-json`): the session has no `AskUserQuestion`, so the orchestrator adopts the recommended option of each question and lists the "Decisions taken without the owner" in the report. The stream carries more than one `result` object (the orchestrator ends its turn while the subagents run in the background and is resumed on each notification): the task result is the **last** `result`.

To turn off in one session only: `WH_PROMPT_GRAPH=0 claude`. To turn off in the project: remove `context.json`. To turn off everywhere: `claude plugin disable wh@wh-harness`. CodeGraph is opened read-only (`mode=ro`); with the index being written at the same time, the query waits up to 1 s and goes on without symbols.

## 7. Extending

**New generic skill**

1. Create `plugins/wh/skills/<name>/SKILL.md` with the procedure and, at the top, the injection:

   ```markdown
   !`cat .claude/profile/_common.md .claude/profile/<name>.md 2>/dev/null || echo PROFILE_MISSING`
   ```

2. Create `plugins/wh/skills/<name>/PROFILE.md` with the template of the `##` sections the skill needs.
3. In the skill body, cite `profile § <Section>`, never a command. Handle `PROFILE_MISSING` by calling `Skill(wh:profile, "<name>")`. Plugin files: `${CLAUDE_PLUGIN_ROOT}/skills/<name>/…`.
4. Bump `version` in `plugins/wh/.claude-plugin/plugin.json` and create the tag `v<version>`.

**New generic hook:** a script in `plugins/wh/scripts/` and an entry in `plugins/wh/hooks/hooks.json` using `${CLAUDE_PLUGIN_ROOT}`. Whatever depends on the project comes from a file in `.claude/profile/`; without that file, the hook exits silently. A hook never blocks: exceptions go to stderr. Test in `tests/` against `examples/demo/`.

**New shell script:** `bash -n` and `shellcheck -S warning` run in CI; a test in `tests/test_scripts.py` builds a temporary repo and exercises the script.

**New agent:** `plugins/wh/agents/<name>.md`; the caller uses `subagent_type: "wh:<name>"` and passes `PLUGIN_ROOT` in the prompt.

## 8. Known limits

- **Lexical, not semantic matching.** "Angry patron" matches "patron", but a paraphrase with no word from the glossary or the index matches nothing. Quality depends on the index keywords.
- **Simplified plural stem.** Irregular forms (`pães`, `colheres`) may not match the singular.
- **A term with a very common name** (e.g. "café", "nível") matches often. Its weight is already split among the features it points at, but it still appears under "Terms".
- **Only names resolve.** CodeGraph links a name to `file:line`; the resolution does not follow calls. Code navigation remains `codegraph explore`.
- **The hook does not see a skill invoked by another skill**, only the text the user sent.
- **An agent worktree with no change is removed when the agent ends** (behavior of `isolation: "worktree"`): that is why QA output, retro and checkpoint go to an absolute path in `<root>/.impl/<slug>/`, and the code QA runs in the clone, without a worktree.
- **Agent worktree isolation guard** (seen in Claude Code 2.1.312): refuses `Write`/`Edit` on a path outside the worktree and refuses the Bash it cannot verify ("too complex to verify": compound command that mentions `git`, `$(…)` substitution, environment variable in front of the command, `env`, heredoc for an interpreter, loop; list in `ENVIRONMENT.md` § Bash in the agent worktree). An Acceptance that only runs outside the worktree gets the "clone only" mark and is run by the orchestrator. That is why the orchestrator creates the `.impl/<slug>/` folders before dispatching agents, and the agents write there through `cat > <path> <<'EOF'`, one simple command per call. If the write still fails, the content comes back in the agent's answer and the orchestrator writes it.
- **Lane continuation by a new agent** needs the branch name free: the old worktree holds it, so the orchestrator saves what is left in it, removes it and deletes the local branch before dispatching (`LANES.md` §3, step 9).
- **A critical or high finding fixed after the phase 4 retest** does not go unchecked: either a short retest of the id only, or the id goes in the `Verify:` field of the final QA prompt, which `impl-qa` checks against the original finding in `qa/<lane|code>.md`.
- **Visual QA screenshots** are born in the final QA's worktree, which disappears with the agent: it copies them to `.impl/<slug>/qa/visual/`, and the orchestrator moves the ones that prove an open bug next to the report.
- **Other Claude Code dependencies in use:** a subagent calls `Skill` (`wh:retro`, `wh:qa-visual`); `disable-model-invocation` hides `implementation`, `deploy` and `brainstorm` from the model (no skill calls them); project hooks run in subagents and worktrees (seen in 2.1.312).
- **PR only with GitHub.** Without an authenticated `gh` or with a remote that is not GitHub, `/wh:implementation` enters no-PR mode in phase 1: it delivers the branch on the remote and the merge command.
- **`.impl/<slug>/` disappears at cleanup.** The task's trail is the report. To debug the harness itself, copy the folder before phase 6 (e.g. a project `PostToolUse` hook that mirrors it, as in the test drive).
- **The plural stem is PT-BR.** In English (`idioma: en`) it cuts the final `s` of any word (`status` → `statu`, `process` → `proces`); since prompt and keys go through the same stem, matching works, but irregular English plurals do not match.
- **Undocumented Claude Code dependencies (to verify on each version):** `preflight.sh` expects the `worktree-agent-*` branch that `isolation: "worktree"` creates (`WH_AGENT_BRANCH_PREFIX` changes the prefix); the orchestrator expects the worktree path in the `Agent` result (fallback: `git worktree list --porcelain`); the answer to a `SendMessage` reaches the agent on its next tool call; a `SendMessage` to an agent that already finished resumes it with its context (that is how the enricher and the QA fixes work); agent worktrees are born in `<repo>/.claude/worktrees/` (phase 1 puts them in the exclude).
